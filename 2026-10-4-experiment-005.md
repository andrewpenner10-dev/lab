# Experiment 005 — Breaking the 10 kbit/s Barrier

**Date: October 4–5, 2026**

## Goal

Experiment 004 ended with what appeared to be a major speed limit.

At a distance of 34.5 cm, the optical link could transmit at:

**200 bit/s with zero errors**

but increasing the raw data rate to:

**250 bit/s**

caused a dramatic increase in errors.

At the time, this suggested that the receiver might be approaching its physical response limit.

The goal of this experiment was to investigate that limit and determine whether the optical hardware itself was actually responsible.

It wasn't.

By changing the way the communication was timed and tested, the same basic optical link ultimately demonstrated error-free communication at more than:

**10,000 bit/s**

The experiment then shifted from finding the maximum bit rate to investigating how long the transmitter and receiver could remain synchronized during a continuous block of data.

---

## Starting Point

The communication system remained:

**Arduino 101 — Appa — transmitter**

↓

**650 nm laser**

↓

**free-space optical channel**

↓

**photodiode receiver**

↓

**Arduino 111 — Momo — receiver**

An important clarification from the previous experiment is that the current receiver uses a **photodiode**, not the LDR used in my earlier LED experiments.

The photodiode has an anode and cathode and responds much faster than the LDR.

This distinction became increasingly important as the data rate increased.

---

## Step 1 — Reconsider the Apparent Speed Limit

Experiment 004 had produced a very sharp transition:

- 200 bit/s — error free
- 250 bit/s — approximately 44% character errors

That initially looked like a physical detector limit.

However, the photodiode should be capable of responding considerably faster than this.

This suggested another possibility:

**The communication code and timing architecture, rather than the photodiode itself, might be the limiting factor.**

The system was therefore reworked to use much finer timing.

Instead of treating milliseconds as the fundamental timing unit, the transmitter and receiver began operating on microsecond-scale timing.

This changed the experiment dramatically.

---

## Step 2 — Break 10,000 bit/s

With the improved timing system, the optical link reached a measured raw data rate of:

**10,526.32 bit/s**

This was more than fifty times the previous error-free record of 200 bit/s.

But simply seeing the receiver decode a few bytes correctly was not enough.

The next question was reliability.

Could the link transmit thousands or tens of thousands of bits at this speed without making a mistake?

---

## Step 3 — Build a Larger Reliability Test

The benchmark was expanded.

Instead of simply checking a small number of characters, Appa transmitted repeated blocks of known data.

Momo compared the received data against the expected data and reported:

- Raw data rate
- Block size
- Blocks tested
- Total bytes tested
- Total bits tested
- Correct bytes
- Byte errors
- Bit errors
- Byte success rate
- Byte error rate
- Bit error rate

This made it possible to distinguish between a byte containing an error and the actual number of incorrect individual bits.

The test used:

**334 blocks per run**

The block size could then be increased while keeping the raw data rate constant.

This allowed a new question to be investigated:

**How long can Appa and Momo transmit continuously before timing errors begin to appear?**

---

## Step 4 — Seven-Byte Blocks

At:

**10,526.32 bit/s**

with a block size of:

**7 bytes**

the system transmitted:

- 334 blocks
- 2,338 bytes
- 18,704 bits

The result was:

**2,338 / 2,338 bytes correct**

**0 byte errors**

**0 bit errors**

**100.000% byte success**

**0.000000% bit error rate**

PASS.

This was already dramatically beyond the previous experiment.

---

PASS.

## Step 8 — Sixteen-Byte Blocks

The block size was increased to:

**16 bytes**

**10,526.32 bit/s**

the system transmitted:

- 334 blocks

**0 byte errors**

PASS.

More than **42,000 individual bits** crossed the optical link without a single detected error.

---

## Step 9 — Find the Block-Length Boundary

The next step was to keep the bit rate unchanged and continue increasing the block size.

At:

**24-byte blocks**

performance degraded substantially.

The system transmitted:

- 8,016 bytes
- 64,128 bits

but produced:

- 526 byte errors
- 797 bit errors

The byte success rate fell to:

**93.438%**

and the bit error rate increased to:

**1.242827%**

This suggested that the problem was no longer simply whether the photodiode could distinguish individual fast pulses.

The link could clearly detect bits at 10,526 bit/s.

Instead, the problem appeared related to how long Appa and Momo could remain synchronized during one uninterrupted block.

---

## Step 10 — Narrow the Boundary

I reduced the block size.

At:

**20 bytes**

the system produced:

- 6,680 bytes tested
- 38 byte errors
- 46 bit errors

Byte success:

**99.431%**

Bit error rate:

**0.086078%**

The result was much better than 24 bytes, but no longer error-free.

I then tested:

**18-byte blocks**

The result was extremely close to perfect:

- 6,012 bytes tested
- 6,011 correct bytes
- 1 byte error
- 3 bit errors

Byte success:

**99.983%**

Bit error rate:

**0.006238%**

Finally, I tested:

**17-byte blocks**

The system transmitted:

- 334 blocks
- 5,678 bytes
- 45,424 bits

Result:

**5,678 / 5,678 bytes correct**

**0 byte errors**

**0 bit errors**

**100.000% byte success**

**0.000000% bit error rate**

Repeated runs produced the same result.

The experimentally observed boundary was therefore extremely sharp:

**17 bytes — repeatedly error free**

**18 bytes — occasional errors**

**20 bytes — measurable errors**

**24 bytes — substantial errors**

This strongly suggests that accumulated timing error within a block is becoming important.

---

## Step 11 — Attempt 12,500 bit/s

With 17-byte blocks working reliably at 10,526.32 bit/s, I attempted to increase the raw data rate again.

The next test was:

**12,500 bit/s**

This time the link failed completely.

Results:

- 5,678 bytes tested
- 0 correct bytes
- 5,678 byte errors
- 21,234 bit errors

Byte success:

**0.000%**

Bit error rate:

**46.746212%**

The bit error rate was approaching what would be expected from data being interpreted almost randomly.

This established another useful boundary.

The current architecture can operate reliably at approximately:

**10.5 kbit/s**

but the tested configuration did not operate correctly at:

**12.5 kbit/s**

---

## Step 12 — An Unexpected New Failure

After the 12,500 bit/s experiment, the physical setup may have been disturbed.

When I returned the code to the previously reliable configuration:

**10,526.32 bit/s**

**17-byte blocks**

the system no longer reproduced its earlier result.

Instead, one test produced:

- 5,678 bytes tested
- 306 correct bytes
- 5,372 byte errors
- 20,122 bit errors

Byte success:

**5.389%**

Bit error rate:

**44.298168%**

I carefully repositioned the laser again, but the result remained essentially unchanged.

This is important because the same configuration had previously transmitted:

**45,424 / 45,424 bits correctly**

multiple times.

The sudden change therefore does not currently appear to represent a newly discovered fundamental speed limit.

Something about the physical receiver, electrical connections, signal level, timing state, or another part of the setup appears to have changed.

Troubleshooting this will be the next step.

---

## An Interesting Observation About Alignment

During the successful testing, I noticed that the exact location of the laser spot on the photodiode may matter.

At one point the beam was positioned somewhat closer to the anode side of the detector, and the link performed extremely well.

It is not yet known whether this was causal or coincidental.

The room lighting also changed during testing, including successful tests with the room light turned on.

Again, there is not yet enough evidence to conclude that the room lighting improved performance.

Both observations are worth testing systematically later rather than drawing conclusions from them now.

## What I Learned

### The previous 200 bit/s limit was not the photodiode's fundamental limit

Experiment 004 appeared to reveal a detector limit between 200 and 250 bit/s.

That interpretation was wrong.

The same basic optical link subsequently operated error-free at more than 10,000 bit/s.

The earlier limitation was therefore associated with the implementation and timing of the communication system rather than a simple inability of the photodiode to respond quickly enough.

### Timing architecture matters enormously

Changing how Appa and Momo coordinate transmission produced an improvement of more than an order of magnitude.

At these speeds, microseconds matter.

Communication performance depends not only on the optical components but also on exactly when the transmitter changes state and exactly when the receiver samples it.

### Bit rate and block length are different limits

The photodiode can successfully detect individual bits at 10,526 bit/s.

However, increasing the number of bytes transmitted continuously eventually causes errors.

The sharp transition around 17–18 bytes suggests that small timing differences between Appa and Momo may accumulate during a block.

Re-synchronization can therefore be just as important as raw detector speed.

### Reliability needs large tests

A communication system working once does not establish that it is reliable.

Testing tens of thousands of bits revealed boundaries that would have been difficult to see by simply transmitting short text messages.

### Zero observed errors is not the same as zero possible errors

A test containing 45,424 error-free bits is strong evidence that the link is working reliably under those conditions.

It does not prove that the true error probability is literally zero.

Longer tests will eventually be needed to characterize the bit error rate more rigorously.

### Physical setup still matters

The sudden loss of performance after previously repeatable error-free tests demonstrates how sensitive a bench-top optical system can be to physical changes.

Alignment, detector position, electrical connections, ambient light, and receiver signal levels all need to be controlled rather than assumed.

---

## Important Limitation

The reported value of:

**10,526.32 bit/s**

is the raw signaling rate of the transmitted data bits.

It should not yet be interpreted as optimized end-to-end application throughput.

Synchronization, framing, block boundaries, and other protocol overhead still consume time.

The purpose of this experiment was to determine how quickly the physical optical link could reliably communicate and how long synchronization could be maintained.

## Next

Before attempting to increase the speed further, the immediate priority is to determine why the previously reliable 10,526.32 bit/s configuration stopped working.

The first diagnostic should be to measure the receiver output under two simple conditions:

**Laser OFF**

and

**Laser continuously ON and accurately aimed at the photodiode**

This will establish whether Momo is still receiving a strong electrical distinction between the optical OFF and ON states.

If the signal levels have changed, the receiver circuit, photodiode position, wiring, or optical alignment can be investigated.

If the signal levels remain strong, the timing and synchronization system can be investigated instead.

Once the previous operating condition has been restored and made repeatable, the next goals are:

1. Re-establish the 10,526.32 bit/s, 17-byte zero-error result.
2. Characterize the 17–18 byte block-length boundary.
3. Determine the maximum reliable raw data rate between 10,526 and 12,500 bit/s.
4. Test longer transmissions to obtain a more meaningful bit-error-rate measurement.
5. Systematically test alignment, ambient light, and photodiode spot position.
6. Continue improving the receiver and synchronization architecture.

Experiment 004 ended with a record of:

**200 bit/s**

Experiment 005 demonstrated:

**10,526.32 bit/s**

The next challenge is to understand exactly why it works — and then make it faster.
