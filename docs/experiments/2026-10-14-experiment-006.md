**Date: October 14, 2026**

## Goal

In Experiment 005, I pushed my Arduino-based laser communication system past 10,000 bit/s, reaching a demonstrated signalling rate of 10,526 bit/s with no detected errors.

That was an exciting milestone, but the system was still primarily a communications experiment. Appa transmitted predetermined test patterns, and Momo verified whether they arrived correctly.

For Experiment 006, I wanted to accomplish two things:

1. Push the optical link to higher speeds while maintaining reliability.
2. Use the laser to transmit an actual computing request, execute it, and display the result on a self-hosted website.

My longer-term goal is to develop three capabilities together:

- **Optical networking:** Laser communication, eventually including pointing, acquisition, tracking (PAT), and multiple network nodes.
- **Internet infrastructure:** Hosting websites and services, implementing real networking protocols, and eventually routing traffic through optical links.
- **Compute:** Running real computational workloads, eventually including distributed computing and AI.

Ultimately, I want to explore putting these systems into space.

This experiment is the first time I've brought all three capabilities together into one functioning application.

## Step 1 — Push the Optical Link to 20,000 bit/s

Experiment 005 had demonstrated reliable communication at 10,526 bit/s using 95-microsecond bit intervals.

I continued improving the timing of the transmitter and receiver.

After progressing through 12,500 bit/s, I reached a new target:

**20,000 bit/s**

At this speed, each bit occupies just 50 microseconds.

That creates a demanding timing problem for two Arduino Uno boards communicating through a laser and an optical receiver.

Both boards must maintain sufficiently accurate timing while transmitting and detecting the optical signal.

The new implementation used tightly controlled microsecond timing, receiver sampling, synchronization, and bounded interrupt handling.

I also continued using a physical button to initiate transmission, with automatic laser shutoff after completion.

## Step 2 — Verify Reliability

Reaching 20,000 bit/s wasn't enough. I wanted evidence that the system could operate reliably over longer transmissions.

I ran two complete physical reliability tests.

Each test transmitted 1,280 packets using eight test patterns.

The results were:

| Measurement | Result |
|---|---:|
| Nominal signalling rate | 20,000 bit/s |
| Packets verified | 2,560 / 2,560 |
| Payload bits verified | 348,160 |
| Detected payload errors | 0 |
| CRC failures | 0 |
| Worst transmitter timing lateness | 7.0 µs |
| Worst receiver timing lateness | 1.5 µs |
| Duration of each test | 45.951 seconds |

Both tests stayed within the specified 8-microsecond timing limits.

The receiver's signal measurements differed slightly between the two runs, but neither test reported a detected payload error.

This established repeatability under the tested conditions.

Importantly, 20,000 bit/s is the nominal signalling rate—not the useful payload throughput. The protocol includes synchronization, framing, and other overhead.

The benchmark's effective payload throughput was approximately 3,788 bit/s.

The system also remains limited by the physical receiver, timing requirements, and manual optical alignment. Zero detected errors in these tests does not establish an error-free link under every condition.

Still, compared with the 200 bit/s demonstrated in Experiment 004, the nominal signalling speed has increased by a factor of 100.

## Step 3 — Move Beyond Test Patterns

With a reliable optical link established, I wanted to make it do something useful.

The question became:

**Could I send an instruction through the laser that would cause a computer to perform an actual computation?**

I decided to build a small computing service.

The first task would be simple: count the prime numbers less than or equal to a specified number.

For example:

**Request:** Count the prime numbers up to 100,000.

**Expected answer:** 9,592.

Instead of transmitting predetermined benchmark data, Appa would transmit a real computing request.

Momo would receive and validate the request, then forward it to software that would perform the calculation.

This required a new application protocol, not just a faster version of the earlier communications benchmark.

## Step 4 — Build the Optical Computing Application

I developed a small system using Python, Arduino firmware, and a locally hosted web dashboard.

The architecture was:

**MacBook Air (job sender)**

↓

USB

↓

**Arduino Appa**

↓

650 nm laser through free space

↓

**Arduino Momo**

↓

USB

↓

**MacBook Air (computing service)**

↓

HTTP

↓

**Web dashboard**

The application contains several components:

- A job sender that prepares and queues computing requests.
- Separate Appa and Momo firmware for transmitting and receiving application packets.
- Packet framing and CRC validation to detect corrupted transmissions.
- A receiving service that validates requests and executes the computation.
- SQLite storage for persistent results.
- A locally hosted website displaying completed jobs and performance measurements.

Each request includes a unique job identifier, the operation to perform, its input parameter, and integrity-checking information.

The receiver rejects malformed, incomplete, or duplicate requests rather than blindly executing them.

I kept the successful 20 kbps firmware archived and developed the computing demonstration separately.

Before uploading the new firmware, the software passed 17 Python tests, additional transmitter control tests, and compilation checks.

Those software tests were useful, but the actual optical demonstration still needed to be performed.

## Step 5 — My First Self-Hosted Computing Dashboard

I also created my first local computing dashboard.

It runs on my MacBook Air at:

`http://127.0.0.1:8765`

The dashboard displays:

- Optical signalling speed
- Delivered payload throughput
- Completed computing jobs
- Rejected packets
- Computing results
- Optical delivery time
- Computation time
- Receiver timing measurements

This introduced me to another part of the system I eventually want to build: hosting my own network services.

The dashboard isn't publicly hosted on the internet. It's a real HTTP service running locally on my Mac.

At this stage, both the sending and receiving software processes run on the same physical computer. The computing request travels through the laser, but the resulting computation and website communication occur locally.

That distinction is important because I ultimately want two independent computers communicating through optical links.

## Step 6 — First Physical Optical Computing Test

On October 14, 2026, I ran the first physical test.

The computing request was:

**Count the prime numbers up to 100,000.**

The process was straightforward:

1. The Mac generated a request and loaded it into Appa.
2. I manually initiated the transmission using Appa's physical button.
3. Appa encoded the request into laser pulses.
4. Momo detected the pulses and reconstructed the packet.
5. The receiving service validated the request and performed the calculation.
6. My local web dashboard displayed the result.

And it worked.

**9,592.**

The result appeared on the dashboard, accompanied by the recorded optical transmission measurements.

This was the first time my laser system successfully transmitted an application request that triggered a real computing job.

## Step 7 — Measure the Results

The first successful physical optical computing test produced the following results:

| Measurement | Result |
|---|---:|
| Request | Count primes ≤ 100,000 |
| Correct answer | 9,592 |
| Packet integrity | 21 / 21 bytes matched |
| Detected CRC / framing errors | 0 |
| Optical delivery time | 33.56 ms |
| Computation time | 1.65 ms |
| Worst TX / RX timing lateness | 6.5 / 1.5 µs |
| Nominal signalling rate | 20,000 bit/s |
| Delivered job payload rate | 4,052 bit/s |

The optical transmission took approximately 33.56 milliseconds.

The computation itself took only 1.65 milliseconds.

The received packet matched the transmitted packet exactly.

The result was saved and displayed on my local website.

The optical delivery measurement excludes USB reporting delays and the time required for the result to appear in the browser. It is not a complete end-to-end latency measurement.

The test demonstrates a successful one-way optical application delivery. A repeat with a different input and a blocked-beam negative control remain to be completed.

## What I Learned

### Fast communication is different from useful communication

In the previous experiments, the central question was how quickly I could transmit information using a laser.

Now I'm beginning to understand how a communication link becomes part of a larger computing system.

The laser isn't performing the calculation. It's transporting an instruction that another computer can execute.

That separation between communication and computation is fundamental to networking and distributed computing.

### Signalling speed and throughput are different

The laser changes its signalling state at a nominal rate of 20,000 bits per second.

But useful application data occupies only part of the transmission. Synchronization, framing, identifiers, and error detection create overhead.

For the optical computing demonstration, the delivered job payload rate was 4,052 bit/s.

Improving the underlying signalling rate is one opportunity. Reducing overhead and making better use of each transmission is another.

### Reliability requires more than receiving the right answer

The result was correct, but I also wanted to know whether the packet was received intact.

CRC validation, exact packet comparison, timing measurements, and persistent records helped establish what happened during the experiment.

Future testing will also need to establish what happens when communication fails.

A useful network must be able to detect failures instead of silently treating them as success.

### A data centre is more than a computer

Even this miniature experiment involves several distinct systems:

- Communication infrastructure
- Compute hardware
- Software services
- Data storage
- Job execution
- Monitoring
- Network access

Developing them together is helping me understand how larger computing and networking infrastructure works.

### Working prototypes create better engineering questions

Earlier, my questions were about how to turn a laser on and off and how to read a photodiode.

Now I'm asking about packet protocols, transmission overhead, hardware UART, distributed computing, hosting, routing, and automatic optical tracking.

Each working experiment creates the foundation for the next.

## Current System

As of October 14, 2026, the laboratory has demonstrated:

**Optical communications**
- 20,000 bit/s nominal signalling
- Two complete reliability tests with 348,160 payload bits verified
- Zero detected errors across those tests
- Packet validation and timing measurements

**Computing**
- A genuine computing request delivered through the laser
- Successful execution of a prime-counting workload
- Correct result: 9,592
- Measured computation time of 1.65 milliseconds

**Hosting**
- A locally hosted HTTP dashboard
- Persistent job records
- Optical-link and computation measurements
- Visibility into completed and rejected requests

The system still has significant limitations.

Communication is one-way. Both software endpoints run on the same Mac. The laser is manually aligned, and the firmware is not yet using hardware UART for optical transmission.

The hosted service is local, and conventional IP traffic is not travelling over the laser.

But the major change is that optical communication, computing, and hosting are now working together in one physical application.

## Next

I want to continue developing all three capabilities in parallel, using my existing hardware before purchasing additional equipment.

The next areas to explore include:

**1. Bidirectional optical communication**

Add a second laser and receiver so Appa and Momo can exchange requests and responses in both directions.

**2. Hardware UART**

Investigate using the Arduino's hardware UART to improve optical communication speed and reduce software timing limitations. This was suggested to me by Mark S. at Protospace. Additional signal-conditioning hardware may be necessary.

**3. Distributed computing**

Move the receiving computing service onto a second physical device so that computation can happen independently of the MacBook Air.

**4. Real networking and hosting**

Progress from custom computing packets toward actual network protocols, remote web hosting, and services accessible through the optical link.

**5. Pointing, Acquisition and Tracking (PAT)**

Develop a system that can automatically find, align with, and track another optical terminal.

Eventually, I want these systems to operate on small satellites, communicating and distributing computing work through optical links in space.

For now, I'm continuing to develop the software and experimental architecture with the hardware I already have.

## Conclusion

Experiment 005 demonstrated that I could transmit information through a laser at more than 10,000 bits per second.

Experiment 006 demonstrated something different.

**I can use a laser to transmit a real computing request, have that request executed, and display the result on a web service that I host myself.**

The first successful job was small.

The answer was simply:

**9,592.**

But the underlying architecture—communication, computation, storage, and hosting—is the beginning of something much larger.

The next challenge is to make these systems independent, bidirectional, faster, and eventually capable of working together across multiple nodes.
